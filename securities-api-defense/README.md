## 1. 인증변환 — RFC 8693 Token Exchange

DMZ·제휴 파트너의 키를 내부 시스템까지 들고 들어오지 않게 합니다.

- 게이트웨이에서 외부 자격증명을 **5분 만료·단일 스코프 JWT**로 교환 (RFC 8693)
- 발신자 인증서 지문을 토큰에 바인딩 (`cnf.x5t#S256`, mTLS) 또는 DPoP
- 내부 서비스는 원 키가 아니라 **교환된 단기 토큰**만 신뢰
- 교환 이력(누가 어떤 스코프로 바꿨는지)을 감사 로그로 남김

## 2. 카디널리티 레이트리밋 — Redis HyperLogLog

IP당 횟수 제한은 공격자가 IP를 바꾸면 무력합니다. **한 토큰이 분당 몇 명의 서로 다른 계정을 조회했는지**를 봅니다.

```text
(토큰, 분) 키에 distinct(account_id)를 HyperLogLog로 누적
distinct(account_id) >= 10  → 즉시 서킷 오픈 + 토큰 폐기 + P1 경보
```

- 정상 사용자는 분당 수 명 수준, 자동화된 대량 조회는 수십~수백 명으로 튑니다.
- HLL은 메모리를 적게 쓰면서 대략적 카디널리티를 셉니다. 정확한 목록이 필요하면 상위 위험 건만 별도 저장합니다.
- 임계치는 서비스별 정상 분포를 먼저 측정해 정합니다.

## 3. IDOR 원천 차단 — 세션별 HMAC Opaque Ref

- 사용자에게 노출하는 리소스 ID를 **세션별 HMAC으로 서명한 불투명 참조값**으로 바꿉니다.
- 미들웨어에서 일괄 검증: 서명 불일치·세션 불일치면 조회 전에 거부.
- 새 API에 개별 검증을 빠뜨리는 실수를 구조적으로 막습니다.

## 4. SQL 인젝션 — CI 차단 + DB 제한

- **Semgrep 규칙으로 MyBatis `${}` 동적 SQL을 PR 단계에서 차단**합니다. `${}`는 문자열 치환, `#{}`는 바인딩입니다.
- DB `max_join_size` 제한으로 대량 조인 유도 공격의 피해를 줄입니다.
- 운영 DB에 **Honey(카나리) 계좌**를 심어 두면 파라미터 변조·SQLi 시 1초 안에 P1 경보가 뜹니다.

## 5. 사고 대응 순서

1. 노출된 관리자 키·토큰 폐기 및 재발급
2. 해당 기간 조회 로그에서 **비정상 카디널리티** 세션 추출
3. 피해 계정 식별·통지, 필요 시 비밀번호·인증수단 재설정
4. 재발 방지 패턴(1~4)을 게이트웨이·CI에 적용
