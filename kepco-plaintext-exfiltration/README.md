# 한전(KEPCO) '저장은 암호문, 유출은 평문' — Encryption at Rest만으로 막지 못한 것

[한국어](README.md) | [English](README_en.md)

2026년 11월 28일, 국회 산업통상자원중소벤처기업위원회 차규근 의원(조국혁신당)이 한전에서 제출받은 자료로 **한전ON과 전자조달시스템에서 암호화해 저장하던 개인정보가 복호화된 '평문' 상태로 유출**됐다는 사실이 공개됐습니다. 같은 자료에서 한전은 **"암호키 유출 및 비인가 접근 정황은 없음"**이라고 답했습니다.

암호키를 훔치지 않고도 암호문이 평문으로 나갔다는 뜻입니다. 이 문서는 사건 사실, 그게 가능한 구조, 그리고 우리 시스템에서 같은 경로가 열려 있는지 확인하는 체크리스트를 정리했습니다.

> 실무자에게 중요한 건 "DB 암호화를 했는가"가 아니라 **평문이 만들어지는 지점이 어디이고, 그 지점에 누가 도달할 수 있는가**입니다.

## 1. 무슨 일이 있었나

- 한전은 한전ON 고객의 **주민·외국인등록번호, 계좌번호, 카드번호를 DB에 저장할 때 암호화**해 왔습니다.
- 그런데 11월 20일 확인된 유출에서는 이 3개 항목을 포함한 **12개 항목 모두가 평문**이었습니다.
- 전자조달시스템도 같습니다. 암호화해 저장하던 기업 대표자 주민·외국인등록번호 **42만 6,827건**이 **"복호화된 평문 상태"**로 유출됐습니다.
- 한전은 암호키를 한전ON은 개인정보처리시스템과 분리된 별도 서버, 전자조달시스템은 DB와 논리적으로 분리된 공간에 이중 암호화해 보관 중이며 **"암호키 유출 및 비인가 접근 정황은 없음"**이라고 답했습니다.

즉 **키가 털려서 복호화된 것이 아니라, 평문이 이미 만들어진 뒤에 그 평문이 나간 것**입니다.

## 2. 왜 키 없이 평문이 나갈 수 있나

저장 시 암호화(Encryption at Rest)는 **디스크에 있는 값**을 보호합니다. 그런데 서비스는 그 값을 화면에 보여줘야 하므로, 어딘가에서 반드시 복호화합니다.

```
[저장]  DB  ── 암호문 (AES 등)          ← 여기까지만 암호화돼 있다
            │
            │  조회 요청
            ▼
[처리]  앱 · API 서버 ── 키 보관소에서 키 사용 → 복호화 → 응답 조립
            │
            ▼
[반출]  응답 JSON / CSV / 화면 / 로그   ← 이미 평문. 키 없이도 그대로 가져갈 수 있다
```

- 공격자가 노린 것은 키가 아니라 **평문을 돌려주는 정상 기능**입니다. 인증된 사용자 한 명, 혹은 인증 검증이 느슨한 조회 API 하나면 충분합니다.
- 전형적인 경로:
  - **BOLA / IDOR**: `GET /api/v1/customer/{no}` 처럼 객체 식별자만 바꿔 남의 데이터를 받는 결함. 고객번호·계약번호처럼 추측 가능한 식별자에서 자주 발생합니다.
  - **과도한 필드 반환**: 화면에는 전화번호 뒷자리만 필요한데 응답 DTO에 주민번호·계좌번호 원문이 함께 실려 나가는 경우.
  - **대량 조회·내보내기**: 목록 API, 엑셀 다운로드, 배치 리포트가 마스킹 없이 원문을 포함.
  - **로그·분석 파이프라인**: 복호화한 값을 디버그 로그나 APM 페이로드에 남기는 경우.
- 그래서 "DB 암호화율 100%"와 "평문 유출 0건"은 서로 다른 지표입니다. **한전 사례는 그 둘이 동시에 성립한 사례**입니다.

## 3. 실무 체크리스트 3종

### ① 민감정보 조회 응답 최소화 · 마스킹 · 토큰화

- [ ] 응답 스키마를 필드 단위로 통제했는가. 엔티티(ORM 객체)를 그대로 직렬화하지 않는가.
- [ ] 화면·API별로 **정말 필요한 필드만** 내려가는가. 주민번호·계좌·카드 원문이 필요한 기능을 목록으로 만들었는가.
- [ ] 목록·검색·자동완성 응답에 민감 필드가 섞여 있지 않은가.
- [ ] 마스킹은 **서버에서** 적용되는가(클라이언트 마스킹은 원문이 이미 전송된 것).
- [ ] 원문이 꼭 필요한 곳은 별도 권한·별도 감사 로그·별도 승인 절차를 두었는가.
- [ ] 로그·APM·에러 트레이스에 평문이 남지 않도록 직렬화 필터를 걸었는가.

### ② 객체 단위 인가와 호출량 통제

- [ ] 모든 조회 엔드포인트에 **객체 수준 인가**(이 객체가 이 주체의 것인가)를 적용했는가. 경로·역할 검사만으로 끝내지 않았는가.
- [ ] 고객번호·계약번호 같은 식별자를 **순차 증가·추측 가능**한 값으로 노출하지 않는가(가능하면 대체 키 사용).
- [ ] 사용자·IP·세션 단위 **조회량 제한(Rate Limit)**과 비정상 패턴(짧은 시간에 다수 객체 조회, 순차 스캔) 탐지가 있는가.
- [ ] 야간·휴일 대량 조회, 신규 디바이스·해외 IP 조회에 경보가 걸리는가.
- [ ] 내부자·운영 계정·배치 계정의 조회도 같은 기준으로 감사되는가.
- [ ] 서비스 계정과 사람 계정의 권한·자격증명이 분리돼 있는가.

### ③ '결함 없음' 체크리스트가 아니라 복호화 데이터 흐름으로 위협 모델링

- [ ] 개인정보 영향평가·내부 점검 항목이 **"암호화 여부"**에서 멈추지 않고, **복호화 이후 평문이 흐르는 경로**를 포함하는가.
- [ ] 데이터 흐름도에 **복호화 지점**(앱 서버, 배치, 리포트, 다운로드, 외부 연동, 로그)이 모두 표시돼 있는가.
- [ ] 각 복호화 지점마다 "누가 호출할 수 있고, 무엇이 응답에 실리며, 얼마나 많이 호출할 수 있는가"를 적었는가.
- [ ] 테스트 계정으로 **타인 객체 조회 시도**가 실제로 실패하는지 자동 테스트가 있는가.
- [ ] 암호화 저장 대상이 늘어날 때 응답 마스킹·인가 테스트도 같이 늘어나는가(신규 필드가 조용히 평문으로 나가지 않도록).
- [ ] 사고 대응 시 "키 유출 여부"만 확인하고 끝내지 않고, **평문이 만들어진 경로**를 추적할 수 있는 로그가 남는가.

## 4. 확인된 것 / 확인되지 않은 것

**확인됨**

- 유출 규모와 항목(한전ON 65만 487명·12개 항목, 전자조달 대표자 42만 6,827건), 유출 당시 평문 상태, 암호키 유출 정황 없음 — 모두 한전이 의원실에 제출한 답변과 개인정보위 신고 내용 기준.
- 신고·조사 진행: 개인정보위 조사 착수(11.23), 국무조정실 공직복무 점검 검토 언급.

**확인되지 않음**

- **어느 계층에서 평문이 만들어졌는지**(앱 로직 오용, 조회 API 결함, 내부자, 배치·리포트 등) — 한전은 "어떤 경로로 복호화된 채 빠져나갔는지"를 조사 중입니다.
- 침입 경로·취약점 종류, 공격자 신원, 유출 데이터의 실제 유통 규모.
- 영향평가가 "결함사항 없음"이었던 구체적 점검 항목.
